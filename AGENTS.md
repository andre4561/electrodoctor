# Электродоктор — контекст для агентов

`AGENTS.md` — общий файл контекста проекта для любого ИИ-агента (Cursor, Codex и др.).
В репозитории, читается из корня.

## Что это

Открытый вычислитель дифференциальной диагностики. На входе анализы, жалобы и данные
осмотра, на выходе 3–4 вероятных диагноза с процентами и разбивкой, какой показатель
сколько добавил к вероятности.

Каждый шаг расчёта это явная формула. Искусственный интеллект используется для
заполнения данных и трактовки рассчитанных выводов, но не внутри самого расчёта.

Исследовательский проект, не медицинское изделие. Все коэффициенты пока условные.

Расчёт делает кабинет (`docs/index.html` → `app/#/clients`): `src/app/signs.ts` по
`docs/data/*.json`. Признаки диагнозов — в `signs.json` (черновики по статьям).

Все статьи лежат в Markdown. На сайте они показываются как HTML: локально их на лету
рендерит `tools/preview.py`, на GitHub Pages — Jekyll. Экспорт и импорт данных — в
формате JSON.

## Где что лежит

- `src/` — TypeScript проекта; кабинет в `src/app/` (анкета, настройки, расчёт `signs.ts`)
- `docs/` — сайт на GitHub Pages; собранный `docs/*.js` и `docs/app/*.js` из `src/` —
  руками не править
- `docs/index.html` — стартовая страница (написана руками, правится напрямую)
- `docs/app/` — кабинет
- `docs/assets/` — общие скрипты сайта: `theme.js` (светлая/тёмная тема), `totop.js`,
  `sitenav.js` (шапка), `articles.css` / `articles-style.js` / `articles-config.js`
- `docs/data/` — данные расчёта кабинета; руками не правятся, собираются из `tools/`:
    - `labs.json` — каталог анализов (коды, синонимы, `group` по материалу) для анкеты,
      распознавания и Настройки → Нормы и веса
  - `norms.json` — нормы и кривые критичности показателей
  - `signs.json` — признаки диагнозов и веса для расчёта вероятностей
  - `diagnoses.json` — разделы специальностей и список диагнозов (`items[файл].sections`)
- `docs/articles/` — статьи в Markdown по разделам (`diagnoses/`, `lab-tests/` и др.);
  у диагнозов в YAML-шапке есть явное поле `sections:` (id вроде `cardio`, `endo`)
- `tools/` — `preview.py`, генераторы сайта, конвейер ИИ-черновиков данных;
  `dx_sections_sync.py` — разовая/повторная запись `sections:` в шапки статей из
  `diagnoses.json`
- `tools/out/` — промежуточный вывод конвейера (в git не входит)
- `tests/` — тесты
- `drafts/` — черновики документов (ещё не в проекте официально): идеология и сырые записи
- `secrets/` — ключи API для скриптов (в git не входит; не дублировать сюда)

## Команды для агента

Что запускать при работе с кодом (не инструкция для пользователя сайта):

```bash
npm run build    # src/*.ts → docs/*.js  (кабинет и прочий фронт)
npm test         # сборка + тесты в tests/
python tools/preview.py   # сайт → http://localhost:8000/
```

### Сайт смотреть только через `tools/preview.py`

```bash
pip install markdown              # разовая установка, единственная зависимость
python tools/preview.py           # → http://localhost:8000/
python tools/preview.py 8080      # другой порт
```

**Корень сервера — папка `docs/`, а не корень проекта.** Поэтому адреса без `/docs`:
`http://localhost:8000/articles/`, `http://localhost:8000/app/`.
С `/docs/articles/` страница не откроется.

Чем этот сервер отличается от простого `python -m http.server`: он на лету превращает
Markdown в HTML, как это делает Jekyll на GitHub Pages. Адрес `…/статья.html` отдаёт
`статья.md`, адрес папки — её `index.md` (если рядом нет `index.html`), разбирает YAML
front matter и берёт `title` оттуда, подключает свой CSS в стиле GitHub со светлой и
тёмной темой. HTML, JS и CSS отдаются как есть. Без него статьи не открываются: в
`docs/articles/` на верхнем уровне лежат только `index.md` и `lab-tests-todo.md`, а сами
статьи — Markdown в подпапках (`diagnoses/`, `lab-tests/` и остальных), готовых `.html`
нигде нет — их делает сервер на лету.

Ещё две причины запускать именно его: `Cache-Control: no-store`, то есть правки видны
сразу по F5, и встроенный посредник `/proxy/<хост>/<путь>` для провайдеров ИИ, которые
не принимают запросы прямо из браузера (YandexGPT, GigaChat). Посредник пересылает
только на хосты из `PROXY_HOSTS`, слушает лишь `127.0.0.1` и ничего не пишет на диск.
`/proxy/ping` отвечает `{"ok": true}` — удобно проверить, что сервер поднят.

Кабинет `docs/app/index.html` по `file://` не работает в принципе: он подключает
`app.js` как `<script type="module">`, а ES-модули подчиняются CORS и с файловой системы
блокируются браузером — страница навсегда висит на «Загрузка…». Корневой
`docs/index.html` этим не страдает (там обычный скрипт), поэтому открывается и из файла.

**Тема сайта** (`docs/assets/theme.js`, ключ `electrodoctor.theme` в `localStorage`):
ставит `html[data-theme="light"|"dark"]`. Кнопка `[data-theme-toggle]` на главной,
в кабинете, в `help.html` и в шапке статей. `preview.py` и Jekyll-шаблон
(`docs/_layouts/default.html`) обязаны подключать `theme.js` **до** `sitenav.js`.
Если на `/articles/` кнопка темы мёртвая и в HTML нет `/assets/theme.js` — крутится
старый процесс `preview.py`, его нужно перезапустить.

## Кабинет: модель данных клиента и анкета

`Client` (`src/app/types.ts`) — пациент: `id`, даты создания/изменения, необязательная
`folder` (подпапка в выбранной папке на компьютере), `values` (все поля анкеты по коду),
собственные `norms`/`curves` (переопределяют общие настройки — см. слои ниже), массивы
`labs: LabSet[]` и `params: ParamSet[]` — сохранённые сдачи анализов и замеры параметров по
датам. `LabSet` / `ParamSet` — одна сдача: дата, время, значения на момент сохранения.
Поля в `c.values` — «открытый бланк»; при сохранении копируются в элемент массива.
Переключение между сдачами подставляет значения в бланк — остальной код работает с
«текущими» значениями без отдельной логики под историю.

Анкета (`src/app/fields.ts`, массив `STEPS`, правится только руками — добавление поля
означает править этот файл) состоит из этапов: general (общее — имя, пол, возраст, жалобы),
params (рост/вес/BMI, давление, осмотр, генетика; часть полей — с историей по датам, как
анализы: `c.params` / `ParamSet`), labs (анализы: полоса дат, загрузка через ИИ, список
только уже появившихся показателей + поиск по справочнику — пустых групп бланка на
вкладке нет; коды бланка по-прежнему в `fields.ts` для ИИ/`inForm`/норм),
studies (исследования: УЗИ/МРТ/КТ/ЭКГ и т.п. — дата, мягкий тип, название, текст
заключения в `c.studies`; без жёстких групп),
psych (психолог) и diagnoses — не анкета, а вкладка с расчётом вероятных диагнозов
конкретного клиента (`drawDxTab()` в `app.ts`, модуль `diagnoses.ts`): разбивка
«за»/«против»/«досдать», фильтр по разделу, ссылка на статью, ссылка **«признаки в
настройках»** → `#/settings/diagnoses/<раздел>/<имя файла статьи>` (сразу раскрытый
диагноз с редактором признаков). Типы полей: text, textarea, date, select, number, yesno,
scale, table (повторяющиеся строки), files (фото/файлы анализов), aiimport (вставка блока
переноса анализов через ИИ).

**Чаты с ИИ** (`src/app/talk.ts`) — два разных режима, не путать:

1. **«Помощник по анкете»** (кнопки на вкладках Общее и Параметры) — агенты
   `intake-general` / `intake-params` в Настройки → Агенты (группа «Общие»). Промпт,
   провайдер, модель и temperature правятся там же, как у остальных; `AGENTS_REV`
   (сейчас 9) поднимается при добавлении в стандартный набор. В system к промпту агента
   дописываются JSON-формат `electrodoctor-talk` и список полей вкладки. Ответ —
   `say` + `set`/`clear`, правки только по полям текущей вкладки (без таблиц/файлов).
   Не ставит диагноз и не назначает лечение.

2. **«Поговорить» у диагноза** (вкладка клиента → Диагнозы, кнопка в строке диагноза) —
   чат с **врачом из Агентов** по `section` диагноза (`Settings.agentsForSections` +
   `agentRuntime`: провайдер/модель/temperature агента). В system идёт `agent.prompt` плюс
   краткий расчёт вероятности и снимок анкеты по `agent.steps` (`clientBrief` /
   `labsSnapshot` — только коды из каталога анализов; остальная нормализация выписки —
   см. TODO).
   Анкету не пишет (обычный текст). Если у диагноза несколько разделов — выбор врача в
   шапке чата. Без врача у раздела (сейчас только «Другое»: Отравление, Потеря
   конечностей, Свищи) — ссылка в настройки агентов.

В шапке обоих чатов: ссылки **настройки** (агент) и **запросы** — HTML-лог сессии
(отправка / ответ / ошибка разными цветами) открывается новой вкладкой
(`openTalkLogHtml`, пока диалог открыт). Ключ API в лог не пишется.

`app.ts` — хэш-роутер (`#/clients`, `#/client/:id/:step`, `#/settings/:tab`) и вся
отрисовка анкеты и вкладок одним файлом.

Справочник анализов кабинета (`src/app/labs.ts`, данные `docs/data/labs.json`) шире
стандартного бланка: показатели с синонимами, типом (`number` / `qual` / `text`) и полем
`group` — раздел по материалу («Кровь», «Моча», «Кал», «Мазки», «Ликвор», «Другие жидкости»,
«Ткань», «Выдыхаемый воздух», «Прочее») и подгруппа внутри него (для крови: общий анализ,
биохимия, антитела, посевы, ПЦР, антигены, иммунология и т.д.). Уровень редкости (`tier`)
в каталоге нет. На вкладке клиента показатель появляется после ИИ, поиска/окна по разделам каталога
(`labpick.ts`) или «Досдать» с диагнозов; новый код в справочник — Настройки → Нормы и веса
(`settings.ts` / разделы из `setlabs.ts`, `settings.labs` → `Labs.applyOwn()`). Значение в `c.values` под тем же кодом.
`qualSign()` разбирает текстовые результаты («обнаружено», «отрицательно»…) через
регулярки на русском и английском — и при ручном вводе, и при сопоставлении ответа ИИ.

Статьи об анализах привязываются к полям анкеты через отдельный захардкоженный словарь
`LAB_ARTICLES` в `src/app/articles.ts` (код → имя файла статьи в `docs/articles/lab-tests/`),
не через поле `article` в `labs.json` — оно используется только как запасной вариант. Новая
статья требует вписать строку в этот словарь вручную.

## Где кабинет хранит данные

Клиент хранится в трёх параллельных местах: `localStorage` (ключ `electrodoctor.clients.v1`,
основное хранилище), опционально в выбранной папке на компьютере через File System Access
API (`folder.ts` — по подпапке на клиента с файлами `client.json`, `анкета.md`,
`данные.csv`; подпапка выбирается по имени один раз и дальше не переименовывается,
конфликты имён решаются суффиксом «(2)», «(3)»), и в `IndexedDB` для бинарных файлов
анализов (`db.ts`/`files.ts` — одна база `electrodoctor`, store `kv` для служебных значений
и `files` для блобов, ключ `"<id клиента>/<id файла>"`, лимит 30 МБ на файл, изображения и
PDF). Файлы анализов, если выбрана папка, дополнительно копируются в подпапку «файлы
анализов» рядом с `client.json`, но сами бинарники остаются и в `IndexedDB` — поэтому файл
открывается даже без доступа к папке.

**Блок «Где хранятся данные»** на `#/clients` (`drawStore()` в `app.ts`): ровно две кнопки —
«Выбрать папку» и «Сохранять в браузере». Отдельной «Разрешить доступ» нет: повторный выбор
папки в системном диалоге снова даёт доступ. Браузер **не отдаёт полный путь** к папке
(только имя) — путь человек может вписать в поле (IndexedDB ключ `folderPath`,
`FS.setPath`); сохраняется по blur/Enter, без лишних кнопок.

Поведение копирования: копия в браузере есть всегда. «Сохранять в браузере» только
отвязывает папку (файлы на диске остаются). «Выбрать папку» → `syncFolder()`: клиенты из
папки подтягиваются в браузер, из браузера пишутся на диск; при одном `id` побеждает более
свежий `updatedAt`, затем всё пишется обратно в папку. Если в выбранной папке уже есть
клиенты — перед синхронизацией confirm; «Отмена» возвращает прежний handle (`FS.restore`).

При старте и при каждом сохранении `syncFolder()` сверяет копию в браузере и в папке по
`updatedAt` и берёт более свежую — это однонаправленная синхронизация по времени правки, не
слияние полей. Настройки синхронизируются аналогично (браузер vs. папка), плюс между
вкладками одного браузера — через событие `storage`, чтобы не затереть более новую версию
настроек устаревшей копией из памяти.

Три уровня хранения, задействованные везде через `try/catch`: приватный режим браузера не
должен ломать кабинет. Проверка поддержки — `folderSupported` в `src/app/setstore.ts` и
`supported` в `folder.ts`. Очистка кэша/данных сайта стирает копию в браузере; файлы в
выбранной папке на диске при этом не трогаются.

## Калибровка вероятности в кабинете (`signs.ts`, `norms.ts`, `curve.ts`)

У диагноза (`docs/data/signs.json`, формат `electrodoctor-signs`, **индексирован по имени
файла статьи в `docs/articles/diagnoses/` без `.md`, не по коду диагноза вроде `D50`** —
переименование статьи рвёт эту связь, если не обновить везде вручную) — список признаков:
`labs` (анализ, направление `dir: up|down|any`, важность `w` 0–10, опционально
`normal: "lower"` — что делать, если в норме), `exam`/`instr` (текстовые признаки осмотра
и инструментальных находок, без кода анализа), `nolist` (нужный анализ не из анкеты, с
опциональным `code` справочника), `prior` (распространённость **в процентах**, не в долях).

Сила отклонения `s` (0…1) считается одним из двух способов, глобальный переключатель —
Настройки → Диагнозы (`signMethod`):
- `"crit"` — критичность показателя (0–100 по кривой, см. ниже) делённая на 100;
- `"dev"` — `min(1, |отклонение от нормы, %| / DEV_FULL)`, норма — отклонение меньше
  `DEV_NORMAL`%. `DEV_FULL = 50`, `DEV_NORMAL = 10`.

Вклад признака (`evaluate()` в `signs.ts`): отклонение в сторону `dir` даёт
`+w × s × K`, в обратную — `−w × s × K` (`K = 0.5` — перевод важности в шаги логарифма
шансов); в норме — `−w × NORMAL_LOWER × K` если `normal: "lower"`, иначе 0; показатель не
сдан — не считается вообще (не 0 вклада, а исключение из суммы, код в `missing`). Если
задана функция `spec` (специфичность, см. ниже), вклад домножается на неё. Вероятность:
`P = 1 / (1 + e^−балл)`, `балл = ln(prior/(1−prior)) + Σ вкладов`, `DEFAULT_PRIOR = 2`%,
если у диагноза своего `prior` нет.

**Открытый вопрос калибровки, важный для архитектуры: способ `crit` берёт готовую кривую
критичности показателя (см. `curve.ts` ниже) и просто делит на 100 — у этой кривой есть
безопасная зона (`SAFE_MAX = 10`: отклонения с критичностью ≤10 считаются нулевой силой).
Эта зона привязана только к показателю (одна кривая на ферритин, одна на ЛПВП и так далее)
и не знает, для какого диагноза сейчас считается сила. Вес `w` применяется позже, уже к
готовой силе, простым умножением `w × s × K`. Из-за этого при `s = 0` (безопасная зона)
вклад всегда 0 независимо от веса — высокий вес не может компенсировать обнулённую силу,
потому что это умножение, а не содержательное взаимодействие. Пример: ЛПВП 1,1 при норме
1,6 (−31%) — это реальный сигнал для метаболического синдрома, но по кривой критичности
такое отклонение ещё в безопасной зоне, и даже при высоком весе ЛПВП для этого диагноза
вклад будет 0. Задача на будущее (TODO.md) — должна ли безопасная зона сужаться для
диагнозов, где показатель весомее, то есть зависеть не только от показателя, но и от пары
диагноз–показатель, и как это сделать без отдельной кривой на каждую пару.** Способ `dev`
этой проблемы не имеет (нет плато), но и не различает лёгкое отклонение от угрожающего —
единые пороги 50%/10% одинаковы для всех показателей, хотя у них разный физиологический
разброс.

Специфичность анализа (`specificity()` в `signs.ts`): чем у большего числа диагнозов
анализ есть в признаках, тем меньше у него вес для каждого конкретного диагноза — иначе
общий показатель (холестерин, СРБ) «поднимал» бы вероятность у десятков диагнозов сразу.
`spec = clamp(SPEC_MIN, 1, ln(N/df) / ln(N/SPEC_FULL))`, где `df` — у скольких диагнозов
анализ в признаках, `N` — сколько диагнозов с признаками всего; `SPEC_FULL = 3`,
`SPEC_MIN = 0.3`. Пример: СРБ есть у 474 из 740 диагнозов → spec 0,3; тропонин у 33 → 0,56;
ПСА у 5 → 0,91.

Кривая критичности (`src/app/curve.ts`) переводит отклонение от нормы в процентах в
критичность 0–100: задаётся отдельно слева и справа от нормы (`L < 0 < R`, разный масштаб
и форма на каждой стороне — несимметрия «рост» vs «падение»), точками `pts` в долях своего
края (−1 — левый край, 0 — норма, +1 — правый), между точками монотонный кубический сплайн
PCHIP (плавный, не выходит за значения точек) либо прямые (`linear: true`). Если кривая
не задана в `norms.json` явно,
`defaultCurve()` строит её по текстовому «типичному интервалу» (`range`, вроде «120–170»
или «до 5»): внутри интервала 0, дальше плавный подъём до 100, края втрое дальше границ
интервала (догадка, не данные). `safeZone()` — зона вокруг нормы, где критичность ≤
`SAFE_MAX`.

Норма и кривая для показателя разрешаются в три слоя (`resolve()` в `norms.ts`, как и
провайдер/модель агента в настройках — общий паттерн кабинета): настройки (`settings`,
общее для всех клиентов) → правило по параметрам клиента (`rule` — `adjust` в
`norms.json`, срабатывает по полу/возрасту конкретного клиента) → своё значение у клиента
(`own`, самый приоритетный слой, правится прямо в карточке). В интерфейсе это три шарика
(серый/фиолетовый/голубой), показывающие, откуда взято текущее значение.

## Настройки кабинета (`#/settings`)

Вкладки по хэшу: Провайдеры, Агенты, Консилиум, Нормы и веса, Осмотр, Диагнозы,
Хранение, Прочее. Код — `src/app/settings.ts`, хранение — `setstore.ts`. Отдельной
вкладки «Анализы» больше нет — каталог слит с Нормами и весами (`#/settings/labs`
перенаправляется). **Вкладка «Консилиум» — пустая заглушка («Раздел в разработке»),
искать в коде там нечего.**

**Провайдеры.** Готовые пресеты (`PROVIDERS`, 4 штуки): OpenAI-совместимый (в скобках
и кнопками адреса — OpenAI, DeepSeek, Mistral, OpenRouter, Ollama, LM Studio), Anthropic,
Gemini, YandexGPT. У OpenAI-совместимого один протокол Chat Completions — меняется только
`baseUrl` (локальный `localhost`/`127.0.0.1` ключ не требует). Старые отдельные id
(`deepseek`, `ollama` и т.п.) остаются в `LEGACY_PROVIDERS` и видны, только если уже есть
в сохранённых настройках. Можно добавить своего (id вида `custom-...`). Список моделей
подтягивается у провайдера по ключу (`models`, `modelsAt`, модели не для чата скрываются),
есть проверка связи (`check`) и флаг `viaProxy`. У YandexGPT отдельно folder ID. Часть
сервисов (OpenRouter, Mistral, Ollama, LM Studio, Gemini) сами сообщают возможности
моделей (vision/pdf/tools/reasoning/free) через API; для остальных возможности
угадываются по названию (`guessCaps()` в `models.ts`) — значки приглушены с пометкой
«по названию».

**Агенты.** Роль со своей инструкцией: какой провайдер и модель использует, temperature,
какие этапы анкеты видит (`steps` из `general`, `params`, `labs`, `studies`, `psych`,
`diagnoses`),
текст промпта. В `DEFAULT_AGENTS`: терапевт, психолог, нутрициолог, два помощника анкеты
(`intake-general` / `intake-params`), врачи по разделам диагнозов (кардиолог, …, генетик)
и координатор. Врачи — хелпер `D(...)`, у каждого свой `section` из
`docs/data/diagnoses.json`. Во всех промптах явный запрет назначать лечение и дозировки.
`AGENTS_REV` (сейчас 9) — версия стандартного набора: при росте недостающие агенты один
раз добавляются к сохранённым (удалённых пользователем обратно не возвращает). У всех
агентов, кроме помощников анкеты, в steps по умолчанию есть «Диагнозы». У
эндокринолога дополнительно поле `examMap` («Карта обследования»). У агентов также
`protocols` («Протоколы») — оба уходят в system чата вместе с `prompt` (лечение и
дозировки по-прежнему не назначаются). Провайдер и модель агента разрешаются в три
слоя — так же, как норма/кривая показателя: своё у агента → общее для всех агентов
(`agentDefaults`) → значение по умолчанию у провайдера. Отдельно от обычных агентов —
распознавание анализов по фото (`recognizer`, физически на той же вкладке): свой
провайдер и модель с тем же трёхслойным разрешением, но это не элемент списка агентов,
а единственная выделенная настройка.

**Нормы и веса** (`drawWeights()` в `settings.ts`) — каталог анализов и редактор норм/кривых
в одном месте. Разделы по материалу (карточки из `setlabs.SECS`: Кровь / Моча / Кал / …);
внутри — чипы подгрупп, «+ Добавить анализ» (`settings.labs` → `Labs.applyOwn()`), тип
показателя (норма / наличие / текст) и кривая через `curve.openEditor()`. У названия —
цифра, в скольких диагнозах анализ в признаках (`Dx.diagnosesUsingLab`): клик — попап со
списком; ссылки ведут в редактор признаков
(`#/settings/diagnoses/<раздел>/<файл статьи>`, новая вкладка), а не в статью — чтобы после
пересчёта сразу править веса. Старый адрес `#/settings/labs` перенаправляется сюда.
У клиента новый код создать нельзя — только из каталога. Правки норм глобальные; у клиента
норма переопределяется в анкете.

**Осмотр** (`exams.ts`, UI — `setexams.ts`, `#/settings/exam`): единый справочник пунктов
осмотра **по системам организма** (не по врачам). У пункта — `entries`: признаки и
вложенные группы (`kind: "group"`, напр. ШКГ); у признака `reply: "scale"|"number"|"text"`
— ползунок 0…100, число или свободный текст; для шкалы края — `from`/`to` (или первая
строка `desc`). Тексты встроенных признаков — статьи `docs/articles/exams/*.md` (раздел
«Осмотры» на сайте); тела для кабинета — `docs/data/exam-descs.json` (сборка
`tools/exam_recover_descs.py` / каркас `tools/exam_write_ts.py`; тела из
готовых статей — `tools/exam_descs_from_md.py`).
У признака поле `article` — имя файла без `.md`. В кабинете описание только
просматривается; правки — локально в Markdown. Код поля: `examId__lineId`.
Vitals пока в `fields.ts`.

**Диагнозы** (`diagnoses.ts` → `draw()`): карточки разделов специальностей;
`#/settings/diagnoses/<раздел>` — список диагнозов (раскрывалки с признаками); с третьим
сегментом хэша — сразу открытый диагноз. Свои признаки поверх `docs/data/signs.json`
(`settings.signs`) и переключатель `signMethod` (`crit` / `dev`) — сила отклонения, см.
раздел «Калибровка вероятности в кабинете» выше.

Привязка диагноза к врачам — это список **разделов специальностей** (`cardio`, `endo`…),
не имена агентов. В шапке статьи: поле `sections:`; в JSON — `items[файл].sections`;
врач в Агентах смотрит на тот же `agent.section`. В списке раздела у каждого диагноза
всегда видны все его специальности (не только «также: …»). Кнопка **«Привязать врачей»**
в редакторе (рядом с распространённостью) открывает диалог: текущие разделы, удалить /
добавить из каталога, сохранить → оверлей `settings.dxSections` (имя файла → id[]),
который перекрывает `diagnoses.json` через `sectionsOf()`. Кабинет **не пишет** в
`docs/articles/*.md` из браузера; чтобы закрепить разделы в репозитории — скрипт
`tools/dx_sections_sync.py` (из текущего `diagnoses.json` в YAML), затем
`python tools/diagnoses_sections.py`.

**Хранение.** Настройки лежат либо в `localStorage` (ключ `electrodoctor.settings.v1`),
либо в выбранной папке файлом `electrodoctor-settings.json` (в браузере тогда только
пометка, что они в папке). Тот же формат при выгрузке «Сохранить настройки в файл». Ключи
API по умолчанию открытым текстом, по желанию шифруются паролем: AES-GCM, ключ из пароля
через PBKDF2, 250 000 итераций, SHA-256 — при включённом шифровании ключи выносятся в
отдельный зашифрованный блок `vault`, в самом файле настроек поля `apiKey` остаются
пустыми. Пароль не хранится нигде — после перезагрузки страницы кабинет просит его снова,
расшифрованный `CryptoKey` живёт только в памяти текущей вкладки. Ключ уходит только
своему провайдеру, когда кабинет отправляет ему фото анализов (`aicall.ts`).

## Перенос анализов через ИИ (`aiimport.ts`, `aicall.ts`, `models.ts`)

Распознавание бланка анализов по фото — три слоя одной функции. `aiimport.ts` сам не
делает сетевых запросов: строит промпт со списком всех полей (`buildPrompt()`) и разбирает
ответ в формате `electrodoctor-labs` (JSON, массив `results`: код/название/значение/
единица/референс/флаг неуверенности). Два пути получить ответ: вручную — человек сам
копирует промпт и фото в любой чат (ChatGPT, DeepSeek, Claude, Gemini, что угодно) и
вставляет текстовый ответ обратно; или автоматически — кабинет сам шлёт запрос выбранному
провайдеру через `aicall.ts`. Разбор ответа и сопоставление с полями анкеты (`AI.match()`)
в обоих случаях одинаковы: код сопоставляется с полем бланка либо ищется в `labs.ts`
(тогда попадает в «Дополнительные анализы»), не нашлось — строкой в «Другие показатели».
Несовпадение единиц измерения помечается отдельно и не переносится автоматически, нужно
подтверждение человека.

`aicall.ts` — сам HTTP-вызов, три протокола: Anthropic (`/messages`, блоки
`image`/`document`), Google Gemini (`:generateContent`, `inline_data`), OpenAI-совместимый
(`/chat/completions`, `image_url`/`file`) — под третий вид попадают OpenAI, Mistral,
OpenRouter, DeepSeek, Ollama, LM Studio и свои провайдеры. GigaChat не поддерживается
вызовом из браузера вообще (`apiOf` → `"none"`) — у него отдельная схема авторизации,
недоступная из клиентского кода. Фото перед отправкой сжимаются в канвасе до стороны не
более 2200px, пережимаются в JPEG, если не уже маленький JPEG/PNG/WebP. PDF отправляется
как есть, но принимают его напрямую только Anthropic, Gemini и OpenAI — остальным нужен
снимок страницы.

## Запросы к ИИ идут через посредника в preview.py

`src/app/models.ts` переписывает адрес провайдера в `${location.origin}/proxy/<хост><путь>`,
когда в настройках включено «Через посредника» (по умолчанию — только у YandexGPT, у него
нет CORS для прямых запросов из браузера). Это следствие: функции ИИ в кабинете работают
только когда он открыт через `python tools/preview.py` — на GitHub Pages посредника нет.
`aicall.ts` и `models.ts` выдают на это отдельную подсказку (`PROXY_HINT`), если `/proxy/`
отвечает 404, 405 или 501.

## Данные кабинета: откуда берутся (`tools/`)

`docs/data/*.json` не пишутся руками, собираются конвейером скриптов, который дёргает
Yandex AI Studio (ключ в `secrets/yandex.json`, не в git) через общий HTTP-хелпер с
повторами при лимитах.

**`labs.json` (каталог анализов).** `tools/labs_catalog_ai.py --model М` разбирает названия
анализов из `nolist` (которых нет в анкете), склеивает синонимы, присваивает код/единицы/
тип → `tools/out/catalog/chunk-NNN.json`. `tools/labs_catalog_build.py` — главная сборка:
берёт поля анкеты (`inForm: true`, `group` из заголовков секций `fields.ts`) + разобранные
ИИ коды, схлопывает дубли по имени/синонимам, подставляет статьи по совпадению названий,
пишет обратно в `signs.json` код справочника для каждого упоминания в `nolist`. В конце
сборки `tools/lab_groups.py` дописывает пустые `group` по материалу («откуда берётся») и
раскладывает кровь по подгруппам (антитела / посевы / ПЦР / антигены / иммунология и бланковые);
можно гонять отдельно: `python tools/lab_groups.py`. Сводка «nolist ↔ каталог / бланк / без кода» —
`python tools/nolist_gap.py` → `docs/articles/nolist-gap.md`. Содержит захардкоженный словарь `REMAP`
(код, который ИИ придумал повторно → уже существующий код) — живой признак того, что
ИИ-черновики периодически изобретают новые коды для уже существующих анализов; с этим же
борется пласт скриптов поиска дублей (`dedup_candidates.py`, `dedup_candidates2.py`,
`ai_dedup.py`, `dedup_apply.py` → `tools/dedup_map.json`, карта дублей, подхватывается
`labs_catalog_build.py` через `REMAP`) и синхронизации названий (`ai_lab_names.py` →
проверенные человеком предложения переносятся в статичный словарь `lab_names.py`,
`lab_names_sync.py` переименовывает файлы статей вслед за новыми названиями).

**`signs.json` (признаки диагнозов).** `tools/ai_signs.py --model М --all|--section S`
читает статью о диагнозе и список анализов анкеты, выписывает признаки (анализы с весом и
направлением, осмотр, инструментальные находки, `nolist`) в `tools/out/signs/<модель>/`.
`tools/ai_signs_merge.py --model М [--overwrite]` сводит черновики в `docs/data/signs.json`
(не трогая уже записанные диагнозы без `--overwrite`). Для сравнения черновиков разных
моделей — `tools/ai_signs_compare.py` (наглядное HTML-сравнение, не меняет данные) и
`tools/signs_compare.py --a М1 --b М2` (автоматическая сверка без ИИ: совпавшее → `auto.json`,
спорное — противоречащие направления, разница весов ≥3 — в `review.json`),
`tools/signs_consensus.py [--apply]` собирает согласованное (`auto.json` плюс решения
человека) в кандидат `signs.json`.

**`norms.json` (нормы и кривые).** `tools/ai_norms.py --model М` для числовых анализов без
нормы просит у ИИ референсный интервал → `tools/out/norms_proposed.json`.
`tools/norms_apply.py` переносит предложения в `docs/data/norms.json` автоматически (без
ручного ревью). Норма одним числом — середина интервала (или половина верхней границы для
«до X»); только нижняя граница («не меньше X») пока пропускается — кривая критичности так
не умеет. Уточнение норм по большим объёмам данных лабораторий — отдельная автоматизация
позже.

**`diagnoses.json` (разделы диагнозов).** `tools/diagnoses_sections.py` раскладывает статьи
`docs/articles/diagnoses/*.md` по специальностям. Приоритет для `sections` у статьи:
1) явное поле `sections:` в YAML (id разделов); 2) словарь `OVERRIDES` в скрипте;
3) пересечение `tags` статьи с тегами раздела из `SECTIONS`; 4) раздел `other`.
Флаги «Дети» / «Пожилые» / «Неотложно» по-прежнему из `tags`. Разовая (и повторная)
запись `sections:` во все шапки из текущего JSON: `python tools/dx_sections_sync.py`,
потом снова `python tools/diagnoses_sections.py` для проверки круга. Список разделов и
их тематических тегов зашит в скрипте (`SECTIONS`).

**Статьи.** `tools/ai_articles.py --mode full|short --model М` пишет статьи для анализов
без статьи (полные — 10 разделов, 6–10 тыс. знаков, для анализов анкеты и показателей с
≥3 ссылками от диагнозов; краткие — 2 абзаца, для остальных); `--replace` переписывает,
`--upgrade` превращает краткую в полную. `tools/ai_articles_review.py --model М` другой
моделью ищет фактические ошибки в написанных статьях → `tools/out/review/<КОД>.json`.
`tools/review_apply.py файл.json` применяет точечные правки (старое→новое, старое должно
встречаться в тексте статьи ровно один раз) и помечает статью «вычитано Claude» в шапке.
`tools/delatex.py` чистит LaTeX-формулы из статей (сайт их не рендерит).

**Публикация сайта (не зависит от ИИ-конвейера).** `tools/preview.py` — см. раздел
«Сайт смотреть только через tools/preview.py» выше. `tools/section_pages.py docs/articles`
пересобирает `index.md` каждого раздела статей. `tools/articles_home.py docs/articles` —
главная страница статей, карточки разделов с SVG-иконками. `tools/lab_articles_todo.py` —
список показателей анкеты без статьи → `docs/articles/lab-tests-todo.md`.
`tools/articles_status.py` — сводка кто написал/вычитал статьи об анализах →
`ARTICLES_STATUS.md` в корне. Меняется состав разделов — правится список `SECTIONS` в
соответствующем генераторе, затем он перезапускается.

### Выкладка на 32rumba.ru (статический сайт, не Jekyll)

Боевой сайт на хостинге — **готовая статика**, собранная локально как `preview.py`
(Markdown → HTML + `articles.css`), а не вывод GitHub Pages/Jekyll. Иначе на хосте
остаются старые Jekyll-страницы, чужая тема и битые стили.

Учётные данные FTP — только в `secrets/ftp.json` (в git не входит): `host`, `port`,
`user`, `password`, `remote_dir`. В чат пароль не писать. SFTP на том же логине/пароле
обычно **не** работает (порт 22 может быть открыт, аутентификация — нет) — выкладка
через обычный FTP (порт 21).

```bash
python tools/build_site.py              # → tools/out/site/ + архивы
python tools/ftp_upload_zip.py          # по умолчанию .tar.gz, иначе .zip
# при необходимости перед выкладкой: python tools/ftp_clean_site.py
```

**Архив для панели хостинга — `tools/out/electrodoctor-site.tar.gz`.** На Linux-хостинге
именно его распаковывать в корень сайта (рядом с `.user.ini` / `.well-known`, их не
трогать). Формат PAX/UTF-8: кириллические имена статей (`АЛТ.html` и т.п.) остаются
читаемыми. `electrodoctor-site.zip` тоже собирается (флаг UTF-8 в ZipInfo), но панель
хостинга при распаковке zip часто ломает имена в кракозябры — **zip на этот хост не
предпочитать**.

В архив **не** входят исходные `.md` статей — только готовый HTML. Если на сервере
лежат `.md`, это старый мусор (Jekyll/ручная копия `docs/`), для сайта они не нужны;
перед чистой выкладкой их лучше снести вместе с устаревшими `articles/`, `assets/css/`
от темы Pages и `_includes/`. Скрипт `tools/ftp_clean_site.py` это делает по FTP
(много файлов — соединение может рваться, есть переподключение; при обрыве можно
дочистить вручную в панели и залить архив заново).

`build_site.py` также не кладёт в выкладку вложенные `.zip` из `docs/` (чтобы не
залить случайно `docs.zip` внутрь сайта). После распаковки `tar.gz` в корне должны
быть `index.html`, `app/`, `articles/`, `assets/`, `data/` — без кракозябр в именах
файлов статей.

## Соглашения

- Собранный `.js` коммитится вместе с исходным `.ts`.
- Новые веса и диагнозы — в `docs/data/signs.json` и конвейере `tools/`.
- Правка собранного `docs/**/*.js` руками запрещена — только через `src/` и `npm run build`.
- Реальные данные пациентов в репозиторий не попадают никогда, даже «обезличенные
  вручную». Только вымышленные примеры.
- Лицензии разные: код AGPL v3, данные и документация CC BY-SA 4.0.
