# Аудит Электродоктора — playbook для ИИ

Этот файл — **инструкция для модели-аудитора**. Цель: пункт за пунктом проверить
проект и записать заключение. **Код, данные и конфиги не менять** — только читать,
запускать проверки и писать отчёт.

Опирается на распространённые схемы аудита (инвентарь → статика/секреты → логика →
отчёт с доказательствами), адаптированные под этот репозиторий: статический сайт,
кабинет в браузере, явные формулы вероятности, JSON-данные, конвейер `tools/`.

Контекст проекта: `AGENTS.md`, `README.md`, `DISCLAIMER.md`, `TODO.md`,
`docs/data-format.md`.

---

## Как запускать

1. Прочитай этот файл целиком и `AGENTS.md`.
2. Зафиксируй в отчёте: дату, модель, **hash коммита** (`git rev-parse HEAD`), ветку.
3. Иди по разделам **по порядку**. Каждый пункт отметь одним статусом:
   - `ok` — проверено, замечаний нет
   - `fail` — есть проблема (заведи находку)
   - `partial` — частично / риск есть, но не блокер
   - `skip` — не применимо **с одной фразой почему** (не пропускай молча)
4. Пиши отчёт в новый файл:
   `audit/reports/YYYY-MM-DD-<кратко>.md`
   по шаблону `audit/REPORT_TEMPLATE.md`.
5. Если времени мало — сначала разделы **A, C, E, F** (карта, секреты, расчёт, данные),
   остальное пометь `skip` с причиной «не хватило времени».
6. **Не исправляй** найденное. Не коммить. Не трогай `secrets/`. В отчёт не копируй
   ключи API, пароли, содержимое `secrets/*`.
7. Можно запускать безопасные команды: `npm test`, `npm run typecheck`, `npm run build`,
   `python tools/nolist_gap.py`, чтение файлов, поиск по репо. Не заливай сайт на FTP,
   не вызывай платные API без явной просьбы человека.

Фраза для старта аудита (можно дать модели как есть):

> Проведи аудит по `AUDIT.md`. Код не меняй. Отчёт сохрани в `audit/reports/`
> по шаблону `audit/REPORT_TEMPLATE.md`.

Фраза для следующего шага у человека в основной IDE:

> Исправь находки из `audit/reports/<файл>.md`, начиная с severity critical и high.

## Формат находки

Каждая проблема — отдельный блок в отчёте:

| Поле | Что писать |
|------|------------|
| ID | `A-01`, `F-03`… (буква раздела + номер) |
| Severity | `critical` / `high` / `medium` / `low` / `info` |
| Где | путь и строки, например `src/app/signs.ts:120-145` |
| Что не так | один-два предложения факта |
| Доказательство | цитата, вывод команды, конкретный пример ввода |
| Риск | что сломается у пользователя / в данных / в безопасности |
| Как проверить после фикса | команда или ручной шаг (без самого фикса) |

**Severity (ориентир):**

- `critical` — утечка секретов, выполнение чужого кода у всех посетителей, порча/потеря
  данных клиентов без восстановления, расчёт явно расходится с заявленной формулой на
  типичных данных
- `high` — ломает основной сценарий кабинета/сборки; XSS в кабинете; ключи уходят не туда
- `medium` — заметный баг или дыра в согласованности данных; нет теста на критичный путь
- `low` — шероховатость, устаревший комментарий, редкий край
- `info` — наблюдение, долг, расхождение с `TODO.md`, не баг

Не вставляй сырой дамп сканера целиком. Сначала подтверди находку чтением кода.

## A. Инвентарь и карта

- [ ] A1. Перечисли точки входа: `docs/index.html`, `docs/app/`, `tools/preview.py`,
      выкладка (`tools/build_site.py`, FTP), GitHub Pages.
- [ ] A2. Где живёт расчёт вероятностей (`src/app/signs.ts`, `norms.ts`, `curve.ts`) и
      откуда данные (`docs/data/*.json`).
- [ ] A3. Где хранятся данные клиента: `localStorage`, папка (File System Access),
      IndexedDB — кратко и с путями к модулям.
- [ ] A4. Где уходят запросы к ИИ (`aicall.ts`, `models.ts`, посредник `/proxy/` в
      `preview.py`) и что **не** должно влиять на формулу вероятности.
- [ ] A5. Что в git не входит: `secrets/`, `tools/out/` и т.п. — сверь с `.gitignore`.

В отчёт: короткая карта (10–20 строк), не пересказ всего `AGENTS.md`.

## B. Сборка, типы, автотесты, зависимости

- [ ] B1. `npm run typecheck` (или `build`) — без ошибок?
- [ ] B2. `npm test` — все тесты зелёные? Что именно покрыто (сейчас мало — зафиксируй
      пробелы как `info`/`medium`, не как «всё плохо»).
- [ ] B3. Собранный `docs/**/*.js` соответствует `src/` (нет правок «только в docs» без
      источника)? Выборочно сравни 1–2 недавно троганных модуля.
- [ ] B4. Зависимости: `package.json` / lockfile; нет ли лишних или подозрительных
      пакетов; при возможности `npm audit` — только подтверждённые findings.
- [ ] B5. Python-часть: импорты в `tools/*.py`, нужен ли `markdown` и что ещё; нет ли
      `subprocess`/сети в неожиданных местах выкладки.

## C. Секреты и чувствительные данные

- [ ] C1. В репозитории и истории HEAD нет ключей, паролей FTP, токенов (поиск по
      шаблонам `api_key`, `password`, `sk-`, `secrets/` закоммичен?). Не выводи секреты.
- [ ] C2. Кабинет: ключи API только в настройках; шифрование vault (AES-GCM / PBKDF2) —
      описано и выглядит связно; пароль нигде не пишется на диск открытым текстом.
- [ ] C3. Ключ уходит только своему провайдеру при вызове; нет логирования ключа в
      `console` / тексты ошибок.
- [ ] C4. Пациентские данные не попадают в git (даже «обезличенные» примеры — только
      вымышленные). `DISCLAIMER` / README не обещают мед. изделие.

## D. Безопасность статического сайта и кабинета

Кабинет — клиентский; «логина сервера» нет. Оцени риски в этой модели, не требуй
классический backend-auth там, где его быть не должно.

- [ ] D1. XSS: пользовательский/ИИ-текст в анкете и настройках экранируется при вставке
      в HTML (`esc` и аналоги). Опасные места: `innerHTML`, шаблоны строк в `app.ts`,
      `settings.ts`, чат, импорт анализов.
- [ ] D2. `docs/assets/site-inject.html` + `site-inject.js`: выполняется у всех
      посетителей; из кабинета писать нельзя; файл в репо пустой или только доверенный код.
- [ ] D3. `preview.py`: слушает только `127.0.0.1`; `/proxy/` только на хосты из
      `PROXY_HOSTS`; нет произвольной записи файлов с веба.
- [ ] D4. На GitHub Pages / 32rumba нет серверной записи настроек — нельзя «сохранить
      сайт для всех» из браузера гостя.
- [ ] D5. Ссылки и `postMessage` / `localStorage`: нет очевидной дыры, через которую
      чужой сайт читает ключи кабинета (same-origin ожидаем).
- [ ] D6. Загрузка файлов анализов: лимит размера, типы; нет исполнения загруженного
      как скрипта.

## E. Ядро расчёта (корректность относительно заявленных формул)

Источник правды по смыслу: `AGENTS.md` (калибровка), код `src/app/signs.ts`,
`norms.ts`, `curve.ts`, при необходимости `docs/data-format.md`.

- [ ] E1. Формула вероятности: `балл = logit(prior) + Σ вкладов`, `P = 1/(1+e^−балл)`;
      `prior` в процентах обрабатывается верно; `DEFAULT_PRIOR` если своего нет.
- [ ] E2. Вклад признака: направление `up|down|any`, вес `w`, сила `s`, множитель `K`;
      обратное направление даёт минус; отсутствие анализа — в `missing`, не ноль-вклад.
- [ ] E3. Режимы `crit` и `dev`: считаются как описано; безопасная зона `SAFE_MAX` в
      `crit` обнуляет силу; задокументированное ограничение (вес не пробивает safe zone)
      — это известный долг, не обязательно `fail`, но проверь, что поведение совпадает
      с описанием.
- [ ] E4. `normal: "lower"` и `NORMAL_LOWER` — в норме снижают вероятность ожидаемым
      образом.
- [ ] E5. Специфичность `specificity()`: границы `SPEC_MIN`/`SPEC_FULL`, не делит на ноль,
      не даёт NaN на пустых данных.
- [ ] E6. Качественные анализы (`qualSign`): типичные рус/англ ответы разбираются; мусор
      не даёт ложного «обнаружено» без оснований.
- [ ] E7. Слои норм `resolve()`: settings → rule → own; приоритет own самый высокий.
- [ ] E8. Кривая: PCHIP/linear монотонность на отрезках; края; `defaultCurve` от `range`
      не взрывается на «до X» / пустых.
- [ ] E9. ИИ **не** участвует внутри `evaluate()` / расчёта P — только данные на входе и
      текст после. Подтверди по коду вкладки диагнозов.
- [ ] E10. Ручной мини-пример: возьми 1 диагноз из `signs.json` и вымышленные значения —
       посчитай ожидаемый знак вклада на бумаге и сравни с логикой кода (не обязательно
       гонять UI). Расхождение формулы и кода = `fail`.

Медицинскую «истинность» весов ИИ **не** оценивай как клинический эксперт: помечай
подозрительные priors/веса как `info`/`medium` (данные), отдельно от багов кода.

## F. Согласованность данных

- [ ] F1. Ключи `signs.json` = имена статей в `docs/articles/diagnoses/` без `.md`
      (выборочно + поиск сирот).
- [ ] F2. Коды в `signs.labs` / `nolist.code` существуют в `labs.json` или честно без
      кода; сверка `python tools/nolist_gap.py` / `docs/articles/nolist-gap.md`.
- [ ] F3. `diagnoses.json` ↔ файлы статей ↔ разделы; нет массовых битых ссылок.
- [ ] F4. `LAB_ARTICLES` в `src/app/articles.ts` → существующие `lab-tests/*.md`
      (это уже частично в `npm test`).
- [ ] F5. `norms.json`: у числовых показателей бланка есть норма или явная причина
      отсутствия; качественные без нормы — ожидаемо.
- [ ] F6. Форматы JSON соответствуют `docs/data-format.md` (выборочно, не весь файл).

## G. Конвейер `tools/` (без запуска дорогих ИИ-прогонов)

- [ ] G1. Генераторы пишут в ожидаемые пути; `tools/out/` в `.gitignore`.
- [ ] G2. Скрипты выкладки (`build_site.py`, `ftp_upload_zip.py`) не тащат `.md` статей
      и секреты в архив; не кладут вложенные zip из `docs/` без нужды.
- [ ] G3. `preview.py` рендерит md→html, front matter `title`, нет path traversal за
      пределы `docs/`.
- [ ] G4. Опасные операции (чистка FTP, upload) требуют явных учётных данных из
      `secrets/` и не вызываются «сами» из кабинета.

Не запускай полный ИИ-конвейер (`ai_signs`, `ai_articles`, …) в аудите по умолчанию.

## H. Кабинет: UX-критичные потоки (по коду)

- [ ] H1. Роутер хэша: `#/clients`, `#/client/:id/:step`, `#/settings/...` — нет явных
      тупиков/опечаток в переходах к признакам диагноза.
- [ ] H2. Сохранение клиента и `syncFolder()`: побеждает больший `updatedAt`; нет явного
      молчаливого затирания новой версии старой без условий.
- [ ] H3. История сдач `labs` / `params`: переключение даты подставляет значения; текущий
      бланк = `values`.
- [ ] H4. Импорт анализов: разбор `electrodoctor-labs`; несовпадение единиц не пишется
      в значения без подтверждения.
- [ ] H5. «Поговорить с доктором»: только поля текущей вкладки; запрет лечения в промпте
      присутствует; без провайдера — ссылка в настройки, не падение.
- [ ] H6. Осмотр: коды `examId__lineId`; справочник из настроек/данных согласован с UI.

## J. Итог аудита

В конце отчёта обязательно:

1. Краткий вердикт (5–10 предложений): насколько проект целостен.
2. Таблица всех находок по убыванию severity.
3. Топ-5 того, что чинить первым.
4. Что сознательно не проверялось (`skip`).
5. Команды, которые аудитор реально запускал, и их код выхода.

---

## Чего аудитор не делает

- Не ставит клинический диагноз и не «утверждает» правильность медицины весов.
- Не переписывает код «заодно».
- Не считает аудит заменой медэкспертизе или сертификации изделия.
- Не публикует отчёт с секретами.

После аудита человек забирает файл из `audit/reports/` в свою IDE и чинит точечно.
